# Adapt the template to an existing project

This is an instruction for the adapting agent. User authorization to configure the workflow authorizes project configuration changes, not application deployment, deleting unrelated work, resuming historical tasks, or replacing user policies.

1. Read the destination AGENTS.md, Git status/worktrees, OpenSpec version/config/schemas/skills, test/build/deploy documentation and existing task sources. Work in an isolated configuration branch/worktree. Preserve dirty files. Do not impose template assumptions over verified project rules.
2. Copy the payload selectively: `.agents/skills/flow-*`, `.agents/references/flow/`, `tools/flow.py`, and `openspec/schemas/flow-*`. Merge `AGENTS.fragment.md` into AGENTS.md under one managed section. Merge OpenSpec config; never overwrite existing context/rules. Keep generated upstream skills intact. Default schema becomes flow-standard for new work only; do not reinterpret old changes automatically.
3. Fill `workflow/project.json` with verified main branch, actual commands, working directories, environment URL, release identity check, durable evidence location, model preferences and deployment authorization. Prefer GPT-6 Sol for implementation, GPT-6 Luna for clear bounded tasks, Spark when available for tiny mechanical edits, and GPT-6 Astra for architecture, complex debugging or an explicit user request. Preserve any explicit model choice; do not add a project-level model pin. An empty command is unresolved, not success. Ask only genuinely missing product/permission questions. The template defaults deployment to not authorized: the project owner may explicitly authorize continuous deployment to their experimental environment, including before acceptance. Record that choice; do not ask again for each authorized change.
4. Use in-repository planning by default: put canonical `openspec/`, schemas, changes and configuration in the code repository; set `planning_layout: in-repo`, `planning_root: .`, `code_repo: .`, the verified `main_branch`, and no `store_id` in `workflow/project.json`. Run OpenSpec from each code worktree without `--store` and run the helper with `--root .`. The helper places locks, leases and live record pointers in the shared Git common directory's `flow/`; these coordinate linked worktrees on one machine, not separate clones. Keep `delivery.json`, recovery history and evidence versioned in the repository. Merge `template/.gitignore.fragment` into the repository ignore rules. If an existing project needs a standalone planning repository, explicitly set `planning_layout: standalone`, keep one shared planning checkout, read the installed `openspec store --help` before configuring a store, and use its canonical root and `--store` on supported OpenSpec calls. Do not silently migrate existing projects or leave two writable planning homes.
5. Move existing canonical specs into that planning home only after reconciliation. Inventory GAME_SPEC-like documents: preserve unique requirements, resolve contradictions, retain an overview with links. Move engineering explanations to architecture docs. Never delete a source before coverage is checked. Update references and instructions. Record the authoritative location; do not leave two writable sources of truth.
6. Import existing tasks deliberately: map each to a change and verified lifecycle stage, retain pauses, questions and acceptance obligations. Unknown delivery is not deployed. Do not resume them. For each newly created change use `openspec new change`, then helper `init`. An initiative is an OpenSpec parent change with child links, not duplicate child checklists.
7. Configure shared resource ownership: helper claim protects a change; a separate integration lease serializes spec sync, code merge and deploy; a planning lease serializes multi-file OpenSpec edits/commits. Acquire using `lease acquire <name> --owner <session-id>`, release in finally. There is no automatic expiry. Investigate interrupted owners before explicit recovery. Never hold a lease waiting for human input. In-repo mode requires an up-to-date main ancestor before `init`, `claim` or `inbox`; the helper pins each changed delivery record to its worktree until publication. Commit and integrate that exact record into main, call `handoff` from the stable main worktree, then remove the owned source worktree. Commit finalization and acceptance updates in main. After ownership is released and the exact record is committed, call `unpin`. Do not delete a worktree while its live pointer still names it. In standalone mode, commit shared planning edits after each coherent update while holding planning lease.
8. Validate all schemas, all three skills, helper tests and representative dry runs in a disposable repository: quick, standard, initiative, blocking question, inline answer, interrupted finalization, human acceptance and follow-up bug. Use two real linked worktrees to check competing claims, shared leases, stale-branch rejection, handoff and record survival after worktree removal. Check that unrelated worktrees remain untouched. Verify standalone mode separately.
9. Commit configuration changes, integrate only within existing authorization, remove only configuration-owned resources after integration. Report exact remaining adoption gates; do not claim complete setup while profile/root/commands are unresolved. Do not deploy the application just to install this workflow.

## Updating

Track source template version/commit in workflow/project.json. Compare and merge updates; never bulk overwrite target customizations. After OpenSpec updates validate schemas and skill behavior. To uninstall, remove only managed files/sections after exporting unresolved records; retain specifications and history.

Existing standalone installations stay in standalone mode when updated. To migrate one deliberately, stop new planning writers, inspect active claims and leases, compare the standalone snapshot with the code repository, and preserve historical decisions and paths. Copy canonical specs, changes and durable evidence into the code repository in an isolated worktree, record a source-to-destination manifest, update references and skills, and switch the profile only after there is one writable source. Test linked-worktree coordination and reconcile each active task before removing access to the old checkout. Do not copy runtime lock/lease files or delete the old store as part of the switch.

## Runner later

A runner uses the same helper and skills: list → choose → claim → work → record evidence → transition. It must honor deployment authorization, dependency thresholds, leases and human questions. Queue state remains in OpenSpec changes. Session/process IDs, usage and evidence stay with the change. Do not add a second authoritative database.
